# 开发交接文档

写给接手继续开发的 AI。动手前先读完“必须遵守”和“容易踩的坑”。

更新于 2026-11-06。测试记录保留了运行日期和硬件，改过玩法或数值后请重跑对应测试。

## 项目是什么

3D 塔防游戏，玩家扮演上帝，花钱改变地形。敌人按地形选路：步行、绕路、搭桥、划船、爬坡、穿隧道。每波分两个阶段：

- **摆放阶段**：可以改地形、放塔、升级和拆塔。按 Ctrl+Z 或点工具栏的撤销按钮，逐步撤回最近 20 次操作。
- **战斗阶段**：地形锁定。按空格或点倍速栏的“暂停”可停住敌人、炮弹和攻击冷却，此时可以建塔、瞄准、升级和拆塔。点“继续”或再按空格，按当前选中的倍速继续这一波。

核心乐趣是“靠改地形操纵敌人路线”。现在有五关，开游戏先进选关界面。

## 必须遵守

用户的要求：

- 和用户用中文交流。界面文字也用中文。
- 画面是柔和的风格化写实，参考 Tiny Glade。用户明确否决过卡通和手游风。
- 只有白天光照，不做黄昏和夜晚。
- 树干保持深色。丁达尔光不能强到晃眼。
- 界面美术柔和舒服。
- 目标玩家使用 RTX 2060 及以上显卡，原定帧率目标为 70 FPS 以上。本机只用于确认游戏能正常操作和完成流程。
- 数值放配置文件，注意架构。
- 如果调用 Codex，用 Astra 模型（`gpt-6-astra`），思考等级 max。

玩法决定：

- **暂时不做**：土方守恒、土层价格。
- **以后再做**：矿工。超高墙以后靠敌人挖隧道或提高堆土费用来限制。
- **暂不考虑**：靠自然侵蚀或塌方的玩法。
- **第一关规则**（2026-11-05 用户放宽）：不动脑子的随手摆放必须输；不改地形、但塔放得好的分开放法允许赢，用户希望难度不要太高。堵一条路或挖隧道能赢；封死两条路要输。改数值后必须重新跑平衡测试：`n_naive_*` 必须输，`a_`、`h_`、`j_` 这些按覆盖最多来放的分开放法输赢都可以。

操作安全：

- **不要关闭不是你启动的 Godot 进程。** 用户同时开着别的 Godot 项目。以前因为按进程名全部关闭，可能打断过用户的测试。
- Git 仓库根目录在 `sakura_valley` 的上一级。本次接手的版本是 `master` 分支的 `371838d`。改动前先看工作区状态，按用户要求提交或推送。
- 编译 `native` 前先关掉本项目的游戏，它会锁住 DLL。

## 环境

- **换电脑接手**。在 Windows x64 安装 Godot 4.7.2，在项目管理器中导入仓库里的 `sakura_valley/project.godot`。等首次导入完成后按 F5，从选关界面启动游戏。
- 仓库随附 `bin/pathcore.dll`。运行游戏和编辑 GDScript 直接使用随附的 DLL；修改 `native/` 下的 C++ 后，才需要安装 Visual Studio 的桌面 C++ 工作负载并重新编译。
- Godot 4.7.2，Forward+。在 Windows 双击 `start_game.cmd` 进入选关。脚本支持本机的 `E:\GoDot\`、原来的版本子目录和 PATH；其他安装位置可用环境变量 `GODOT_EXE` 指定可执行文件的完整路径。
- 寻路和战斗用 C++ 写成 GDExtension，直接用 C API，没有 godot-cpp，也不需要 Python。
- 运行 `native\build.cmd` 会通过 vswhere 查找已安装的 Visual Studio x64 C++ 工具，并生成 `bin\pathcore.dll`。
- 11 月 5 日的帧率记录来自 RTX 4060 笔记本版。11 月 6 日本机测试时，Godot 实际选用了 Intel Iris Xe。
- 窗口基准是 1920×1080，拉伸模式 `canvas_items`、`expand`。

## 关键设计

**摆放阶段撤销**。地形笔刷和预设、挖填隧道、建塔、升级、升星、瞄准和拆塔共用一份历史。连续画一笔或拖动一次瞄准滑块各算一步。开战时清空历史，下一波摆放时重新记录。步数由 `data/terrain_tools.json` 的 `brush.max_undo` 控制。

新增陷阱或附魔时，在该功能成功修改状态后调用 `history.record(名称, 撤销回调, 可选的释放回调)`。由该功能保存受影响的数据和实际收付金额，撤销时只反向结算这一笔。摆放阶段拆除的塔会保留原对象，直到撤销、开战或该记录被淘汰。

**地形**：513×513 的高度图，覆盖 320 米。状态存在一张 GPU 贴图里，地形、草、石头都读它。寻路用隔一个点取一个的 257×257 网格，每格 1.25 米。

**隧道**：高度图做不出真正的洞，所以隧道是路线图上连接两个洞口格子的一条边，两端再挖出路堑、放上洞口模型。敌人在隧道里隐藏，也打不到。

**寻路**：从家园向外跑多模式 Dijkstra，代价单位是秒，每个兵种一张流场。`goal_radius` 让家园一圈格子都算终点。模式编号：步行 0、爬坡 1、划船 2、搭桥 3、终点 4、走已有的桥 5、隧道 6。路线对比靠限制可用模式（`option_costs`）或强制经过某点（`via_costs`）多跑几次搜索，每隔一帧跑一次，避免掉帧。

**炮塔升级**：

- 树写在 `towers.json` 的 `upgrades`，任意深度。脚本按路径从上往下叠 `change`，再乘星级伤害，得到这座塔的数值（`tower_manager.spec_for`），用 `set_tower_stats` 一次推给核心（14 个浮点，顺序见 `path_core.h`）。
- 核心里的新效果：燃烧地面（同一个敌人只吃最热的一块火，不叠加）、减速、把爬坡的敌人打回开始爬的格子并躺 1 秒、按塔比目标高多少加射程。
- 已建的塔用 `tower_visibility(id)`、`tower_covered(id)`、`tower_best_aim(id)` 按它自己的圆锥计算。
- 拆塔返还建造和所有升级花费的 70%。不能换分支。
- 重炮原来是 40 伤害、1.2 秒、2.5 米、2 人，人群里比基础塔还弱，导致“堵西路 + 重炮分支”会输。现在是 50、1.0 秒、3.5 米、4 人。
- 平衡测试的 h_ 和 i_ 系列：每座塔按计划升到某个终极形态（第一波只买塔，之后先升级再买新塔）。分开放塔仍然要输，堵西路仍然要赢。

**投石塔和狙击塔**：

- 核心里的圆锥多了 `min_range` 和 `lob`。抛射的塔按水平距离算射程，不检查视线；石头沿抛物线飞，跟着目标落下（不会打空），画在单独的 `stones()` 缓冲里。
- 伤害在开火时按“塔比目标高多少”加成（`height_damage`）。
- 放塔预览用 `stats_visibility`、`stats_covered`、`stats_best_aim`，传入整套数值，所以预览和建好以后完全一致。
- 调数值的过程：投石塔一开始（射程 48、6 人、伤害 10、高度最多 +30）在“不改地形分开放塔”时也能赢，因为第一关两条路都在山谷里，旁边的山坡天然就给满加成。现在射程 42、伤害 8、最多 8 人、高度最多 +27：分开放要输，堵西路剩 6 点生命赢，和炮塔一样。
- 狙击塔是单体伤害，敌人挤在一起对它没有好处，所以它不可能是第一关的主力：120 伤害、2 秒一发时，分开放反而全血赢；现在 3.2 秒一发，只放狙击塔两种打法都输（`k_block_sniper` 的预期就是输）。它的用处是在远处补刀、打爬墙的兵。
- 升级树里的数值是我定的，用户还没看过。

**第一关为什么这样设计**：

- 如果是单体伤害，分兵后塔和敌人同比例减少，集中没有好处。所以塔有范围伤害：敌人合流后更密集，每发打中的人更多。
- 有两个入口，敌人默认才会分开。两条路从家园两侧进来，塔的 70° 圆锥和 55 米射程看不到两边。入口附近禁止建造，两入口之间有矮山脊挡视线。
- 每发最多打中 5 人（`splash_targets`）。没有上限时，砌墙让敌人减速挤成一团，封死两条路反而变强。
- 封死两条路后敌人不会卡住，而是爬过东边的土堤，约 126–142 秒到家。
- 土堤宽 12 米（原来 15 米）。土堤自动伸长后变长了，收窄是为了让价格回到原来的水平（堵西路约 1950 金），否则“堵西路”会因为少买一座塔而输。
- 平衡测试里，机器人轮流在几个区域放塔时，遇到没有敌人经过的区域会改去别的区域买，不会提前停手。以前“封死两条路”因此只买了 1 座塔。
- 攀爬兵会直接翻过土堤，所以堵路后第三波西边仍有漏网，这是有意的压力。

## 怎么运行和测试

在含有 `project.godot` 的 `sakura_valley` 目录打开 PowerShell。以下命令使用本机的控制台版 Godot：

```powershell
$g = "E:\GoDot\Godot_v4.7.2-stable_win64_console.exe"
```

撤销回归覆盖塔和地形交错操作、隧道、金币、步数上限及跨波次行为。固定时间步使拖动和动画可重复：

```powershell
& $g --headless --fixed-fps 60 --path . --script res://scripts/undo_test.gd
```

暂停回归覆盖出兵、移动、炮弹、攻击冷却、暂停期间的塔操作和恢复倍速。

```powershell
& $g --headless --path . --script res://scripts/pause_test.gd
```

重跑第一关的 23 种打法（无画面，改数值后必跑）：

```powershell
& $g --headless --path . -- --balance=all
```

第一关全流程（模拟真实鼠标键盘，会截图到指定目录）：

```powershell
& $g --path . -- --leveltest=D:\Temp\level
```

失败和“再来一次”：

```powershell
& $g --path . -- --leveltest=D:\Temp\lose --lose
```

旧测试要加 `--level=sandbox`，把最后一个参数换成 `--brushtest=目录`、`--pathtest=目录`、`--towertest=目录`、`--uitest=目录` 或 `--uilayout=目录`：

```powershell
& $g --path . -- --level=sandbox --uitest=D:\Temp\ui
```

土堤放偏的容错扫描（西路 5 个角度 × 5 个前后位置 × 11 个左右位置，看有几个能把西路敌人赶到东路）：

```powershell
& $g --headless --path . -- --ridgesweep
```

其他关的平衡测试（打法在 `data/levels/level_0X_balance.json`）：

```powershell
& $g --headless --path . -- --level=level_03 --balance=all
```

看一关：每个入口每个兵种走哪条路、多少秒、怎么走，再给每个镜头截图（目录留空就只打印路线）：

```powershell
& $g --path . -- --level=level_02 --levelcheck=D:\Temp\lv\l2
```

在 `--levelcheck=` 后面再加：`--play` 不放塔、家园不会倒，把每一波都跑完，看有没有人卡住；`--dam=40,-110` 在那里堆一个圆土包再看路线和水；`--uishot=文件` 带界面截一张开局图。选关界面截图：`--menushot=文件`（不加 `--level`）。

其他参数：`--shots=目录 --list=strategy,north` 截图，`--perf=strategy` 测渲染开销。

特效：`--fxdemo=目录` 在空地上把每种命中、开火、倒下、升级各播一遍并截图（会隐藏所有树）。`--fxx= --fxz=` 选地点，`--fxdist= --fxpitch= --fxyaw=` 调镜头。`--fxtest=目录` 在第一条路线旁放三种塔和一座焚地炮，在附近刷一波敌人并截图。加 `--fxnotrees` 隐藏树；加 `--fxmany=24 --fxcount=150 --fxspeed=4` 测满屏特效时的帧率。例：`--level=level_01 --fxdemo=D:\Temp\fx --fxx=0 --fxz=60 --fxdist=45 --fxpitch=-25`。

看结果：搜索日志里的 `BALANCE`、`LEVEL`、`UI`、`TEST`、`ROUTE`、`BRUSH`。脚本解析错误会让测试一直挂着不退出，超时时先看 stderr。日志是 UTF-8，PowerShell 直接显示中文可能乱码。

## 第二到第五关

用户的要求（2026-11-05）：一口气做 3–5 关，开游戏能选关，每关地形不同，可以很奇怪（浮空岛、悬崖），玩家要动脑子改地形才能赢。数值只要差不多，用户会亲自试玩调整。

地图都用 `composed_shape.gd` 按关卡文件里的地貌列表拼出来，写法见 `data/README.md`。

| 关卡 | 地形 | 敌人默认怎么走 | 设计的解法 |

新机制：

- **悬空**：`void_level` 以下的地面在核心里所有移动都是无限代价（`edge_cost`），只能靠桥连接（桥最长 45 米）。地图下方画一层云海挡住地面。玩家把地挖到云海以下就是把地挖穿；工兵造的桥两头的地面一变，桥就没了。塔不能建在云海上。
- **流动的水**：`flowing_water` 打开后，`refresh_water` 只从水源格子灌水，不再从所有一开始有水的格子灌，所以筑坝能让下游的河干掉。只有第四关打开，第一关和试验场不变。

## 容易踩的坑

- `terrain.setup(level["map"])` 必须在 `terrain.build()` 之前调用。
- `ClassDB.instantiate("PathCore")` 的结果放在无类型变量里。对无类型值用 `:=` 会解析失败，要写明类型。
- JSON 里的数字都是浮点数，显示前要转 `int`，否则会出现 `1000.0`。
- `TerrainTools` 要排在 `TowerManager` 之后，`TowerManager` 排在笔刷之后。`_unhandled_input` 后加的节点先收到，靠这个顺序抢点击。
- 土堤 `yaw = 0` 时长边沿 X 轴，这才是横跨南北向道路的方向。
- 土堤靠 `TerrainData.fit_ridge` 自动伸长：沿长边往两头找，直到中线和两侧各半个宽度处的天然地面都高过堤顶（点击处地面 + `height`）。在 `max_length` 内找不到高地的一头算“没接上”，预览立红柱。玩家没滚过滚轮时，`TerrainTools.fit_preset` 会在半圈 12 个角度里挑两头都接上、最短的那个；没有角度能接上就保持原角度。滚轮一转就改为手动。第一关堵路的参考位置是 `(±112, -15)`。
- 玩家定的尺寸存在 `TerrainTools.sizes`（按预设 id），`shaped()` 把它套到预设上。`stretch` 控制土堤是否自动伸长，拖动长度滑块会把它关掉；关掉后也不再自动转向，保留玩家的角度。界面在 `GameUI._sync_preset_sliders` 里同步，自动伸长时长度滑块显示伸长后的长度。
- 平衡测试和容错扫描都通过 `tools.fit_preset` 放土堤，和玩家拿到的形状一致。改土堤逻辑后两个都要重跑。
- 敌人会斜着走来降低坡度，所以光加高土堤效果有限，先检查有没有缺口。大山北侧山脚很缓，那里的土堤要伸到 70 米外才接上，所以 `max_length` 设成 230。
- 水的判断用 `water_mask`，不要用高度，干坑也可能低于水位。
- 改 C++ 接口要同时改 `path_core.h`、`path_core.cpp`、`binding.cpp`，并重新编译。
- `--lose` 测试点“再来一次”后，旧的测试协程会报几条 `get_tree` 空值错误，这是测试本身造成的，不是游戏问题。
- 代码注释用英文，保持现有风格。
- 项目的主场景是 `menu.tscn`。选关界面发现有命令行参数就直接跳进 `main.tscn`（只在第一次进入时这样），所以所有测试命令照旧。选中的关卡放在 `GameConfig.chosen_level`（静态变量，换场景不会丢），`--level=` 参数优先。
- 通关记录存在 `user://progress.cfg`。
- 这台机器上的 Bash 工具会先吃掉一层反斜杠，perl / sed 替换里的 `\n`、`\b`、`\T` 会变成真正的换行、退格或者直接消失。改 JSON 和文档里带反斜杠的内容用 Edit 工具，或者在 perl 里写 `\x5c`。JSON 字符串里出现真正的换行时，Godot 也能读，但它不是合法 JSON。
- 新关卡的地貌按列表顺序叠加，后面的会盖住前面的。浮空图里，家园周围的压平只作用在已经是陆地的地方，不会凭空在云海上造出地面。
